# Event Feed Source Contract

## Decision

Services that expose an internal event feed should publish from a durable,
append-only event log owned by the source service.

This convention prepares the current polling-based event feed pattern for reuse
without introducing Kafka, SNS/SQS, EventBridge, or a central event service.

## Source Responsibilities

A feed source service owns:

- Deciding which business actions emit events.
- Persisting emitted events in its own database.
- Exposing a cursor-based internal HTTP feed.
- Protecting the feed with a technical JWT scope.
- Defining event payloads and schema versions.
- Defining event retention and recovery expectations.

The feed source must not build the feed by polling current state tables or by
comparing snapshots. Consumers need a durable ordered event log.

## Event Log

The source service should persist events in an append-only table shaped like:

```text
EVENT_LOG
  cursor
  event_id
  event_type
  subject
  occurred_at
  payload_json
  schema_version
  created_at
```

`cursor` is the monotonic feed position. It should be generated by the database
or by another source-local mechanism that preserves ordering.

`event_id` is a stable unique identifier for idempotent processing. It is not a
cursor and must not be reused.

`subject` identifies the user, account, profile, subscription, or aggregate the
event is about. The exact meaning is source-specific.

`payload_json` contains event-specific data. Small events may duplicate common
fields at the top level for convenience, but consumers should not infer missing
business state by querying the source synchronously.

## HTTP Feed Shape

The default internal endpoint shape is:

```http
GET /api/internal/events?after=<cursor>&limit=<n>
```

Domain-specific paths are allowed when they make ownership clearer:

```http
GET /api/internal/identity-events?after=<cursor>&limit=<n>
GET /api/internal/profile-events?after=<cursor>&limit=<n>
```

The response should use `items`, `cursor`, `nextCursor`, and `hasMore`.
Common event fields should be top-level. Event-specific fields may remain
top-level for simple feeds, matching the current identity and profile feed
shapes:

```json
{
  "items": [
    {
      "cursor": 126,
      "eventId": "uuid",
      "eventType": "USER_REGISTERED",
      "subject": "user@example.com",
      "occurredAt": "2026-06-03T12:00:00Z",
      "registrationId": "uuid"
    }
  ],
  "nextCursor": 126,
  "hasMore": false
}
```

```json
{
  "items": [
    {
      "cursor": 31,
      "eventId": "uuid",
      "eventType": "PROFILE_CREATED",
      "subject": "user@example.com",
      "occurredAt": "2026-06-03T12:05:00Z",
      "profileId": "uuid"
    }
  ],
  "nextCursor": 31,
  "hasMore": false
}
```

Consumers should request events with `after=<last processed cursor>`. A source
should return events with cursor values greater than `after`.

The source may return an empty `items` array with `nextCursor` equal to the
requested cursor or the current high-water mark. Consumers must use item cursors
as the authoritative checkpoint after successful item processing.

When event-specific data grows, prefer adding an explicit `schemaVersion` and
`payload` object in a new contract version instead of growing unbounded flat
fields.

## Emission Rules

Only explicit business flows should emit feed events.

Examples:

- `identity-svc`: public registration emits `USER_REGISTERED`.
- `identity-svc`: user email confirmation emits `EMAIL_VERIFIED`.
- `profile-svc`: initial profile creation emits `PROFILE_CREATED`.

Administrative, support, migration, backfill, and internal maintenance actions
must not emit feed events by default. If they need to emit events, that should
be an explicit product or operational decision.

## Security

Internal feeds should require a technical JWT scope. Scope names should be
source and capability specific:

```text
token.identity-events.read
profile.profile-events.read
```

Human roles such as `ADMIN` should not be the only protection for service feeds.

## Retention

Each source must define how long event log rows are retained.

If a consumer's stored cursor is older than the retained event window, automatic
polling cannot recover safely. That case requires an explicit resynchronization
or backfill path.

## Library Extraction

Do not extract a shared event-feed library from a single producer/consumer pair.

The current implementation is a candidate for shared infrastructure, but the
first step is to keep source and consumer contracts consistent. Extract a
library only after a second real feed proves that the common mechanics are
stable across services.
